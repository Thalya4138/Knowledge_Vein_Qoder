# 资源发现与整合 Prompt

**版本**：v1.0 · 2026-11-12
**所属**：01 学习工作台
**背景**：用户不只带自己的材料来，也期待系统**主动帮他找**并**整合**。

---

## 0. 边界先说清

| 能做 | 不能做 |
| --- | --- |
| 依据用户给定主题，提出**公开、有许可**的候选资源 | 绕过付费墙、批量抓取需登录的教材 |
| 比较多个来源对同一概念的解释差异 | 把网上内容当成"用户已有的知识"直接写进讲义 |
| 标注每份候选的许可、可访问性、可信度 | 未经勾选就纳入引用 |
| 指出用户材料**缺了**什么（哪些先修没覆盖） | 假装读过它没读到的内容 |

**核心原则**：发现是**建议**，不是**采集**。采纳与否是用户的动作。

---

## 1. 输入

```jsonc
{
  "kbId": "kb.linear-algebra",
  "intent": "补齐第 3 章缺的来源",
  "chapter": { "id": "ch.03", "title": "三种「最近」是同一个问题吗", "goal": "..." },
  "existingResources": [
    { "id": "res.demo-authoring-note", "origin": "generated", "title": "..." }
  ],
  "gaps": ["本章无外部来源", "缺仿射子空间的定义依据"],
  "level": "本科一年级",
  "policy": {
    "allowWeb": true,
    "allowPaid": false,
    "languages": ["zh", "en"]
  }
}
```

## 2. 输出契约

```jsonc
{
  "status": "ok" | "no-reliable-source" | "needs-web",
  "candidates": [
    {
      "id": "res.discovered.xxx",
      "title": "MIT 18.06 Linear Algebra",
      "author": "Gilbert Strang / MIT OpenCourseWare",
      "kind": "video-course",
      "uri": "https://ocw.mit.edu/...",
      "license": "CC BY-NC-SA 4.0",
      "language": "en",
      "trust": "high|medium|low",
      "trustWhy": "大学公开课，与主题直接对应；但为英文，且需自己定位到具体讲次。",
      "fillsGap": ["本章无外部来源"],
      "mappingHint": "第 16–17 讲讨论投影与最小二乘",
      "limitations": "许可为 NC，不得用于商业用途；讲义引用需注明出处。",
      "status": "candidate"
    }
  ],
  "conflicts": [
    { "topic": "投影的定义", "sources": ["...", "..."], "difference": "一处要求内积空间，一处只讲 ℝⁿ" }
  ],
  "stillMissing": ["仿射子空间的定义——公开材料普遍假定读者已知"],
  "recommendation": "先采纳 1 条英文公开课作为对照，本章仍保留本项目原创论述为主干；不要因为补了来源就删掉自己的推导。"
}
```

**三条硬规则**：

1. **`stillMissing` 必须诚实。** 找不到就写找不到，这是最有价值的一栏。
2. **`limitations` 必须有。** 没有一份来源是没有局限的。
3. **`status` 永远是 `candidate`。** 你无权替用户采纳。

---

## 3. 整合 ≠ 拼贴

当用户采纳多份来源后，讲义里如何处理：

| 情况 | 做法 |
| --- | --- |
| 多来源说法一致 | 用一份主来源，其余放"另见"，不重复引用 |
| 说法不同但都成立（条件不同） | **并列，并说明各自的条件** —— 这正是讲义最有价值的地方 |
| 说法冲突 | 呈现冲突，说明可能原因（定义约定不同 / 教材错误 / 版本差异），**不选边** |
| 来源与用户笔记冲突 | 优先保留用户内容，把冲突做成批注让用户决定 |

**禁止**：把三份来源的句子各取一段拼成一段"综合结论"。那不是整合，是掩盖分歧。

---

## 4. 输出到 UI

资源库页（见 `PRODUCT_SPEC.md` §3.6）显示候选时，必须能一眼看出：

- 这是**别人给的**（`origin: discovered`，视觉上与用户导入区分）
- 它**填了哪个洞**
- 它**的局限是什么**
- 采纳 / 拒绝 / 稍后

拒绝时记录原因，用于后续推荐的收敛。

## 5. 自检

- [ ] 每条候选有 license 与 uri（可核对）
- [ ] 每条候选有 limitations
- [ ] 至少一条 `stillMissing`
- [ ] 没有把 discover 的内容说得像已经读过全文
- [ ] 冲突被呈现，未被抹平
- [ ] status 全为 candidate

## 6. 实时联网检索路线（#83，2026-11-26）

用户配了博查搜索 key 时，资源发现走 `ai/search.ts` 实时检索，不经过本提示词。候选的诚实约束与模型路线相同：

- license 一律「待核对」（搜索引擎不给许可信息）；limitations 写明「内容与许可未核对，采纳前请自行核对」；
- trustWhy 只写检索命中的事实（站点名、日期），不得写成「读过全文、认为可靠」；
- mappingHint 取检索摘要，不得当作全文论据；
- 搜索失败 / 无命中：如实说明后降级到模型路线或预置样例，不伪造搜索结果；
- status 一律 candidate，采纳仍是读者的动作；讲义只引用不复制。
